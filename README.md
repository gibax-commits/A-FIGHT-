## 開発上の制約

**画像は必ず `assets/` に外部ファイルとして置く。** HTMLへのbase64埋め込みは行わない。以前は埋め込んでいたが、画像5点でファイルの56%を占め、必要素材は約166点あるため破綻する。外部化により本体は651,706文字から213,344文字まで縮んだ。

**`index.html` を差し替えるときは、ダウンロード前に古いファイルを消しておく。** `index (1).html` のまま上げると、リポジトリに新旧2つが並び、GitHub Pagesは古い `index.html` を配信し続ける。

**JSファイルの分割は簡単ではない。** Babel standalone は各スクリプトを別々のスコープで評価するため、単純に分けると `const` が他のファイルから見えなくなる。分けるなら `window` 経由にするかESモジュール化が必要で、どちらも広範囲の修正になる。

**チャット内プレビューでは画像が表示されない。** 外部ファイル参照はサンドボックス環境で読めないため、動作確認はGitHub Pagesかローカル保存で行う。

styles.css は Tailwind CLI で生成する。設定は tailwind.config.js にある。

コード npm ci
npm run build:css

Tailwind v3.4.19・既定テーマ・プラグインなし。styles.css に独自ルールは1行も含まれず、
Tailwindの出力だけで構成されている。カスタムのスクロールバー指定などは
index.html 側の <style> にある。

以前の styles.css は index.html を走査しただけのビルドで、その時点で書かれていた
クラスしか入っていなかった。sticky tracking-wider grid-cols-3 text-base といった
よく使うものが軒並み欠けており、新規画面を作るたびに制約が効いていた。

現在は safelist でレイアウト・余白・サイズ・文字・枠・効果の各ユーティリティと、
全パレットの text- / bg- / border- / from- / via- / to- を先に出してある。

index.html を編集しただけでは CSS は古くならない。

## 実装済みの主要システム

戦闘はレーン制の交互行動制。プレイヤーが1行動するたびに敵も1手番動く。AP(行動力)は毎ターン5に回復し、移動・攻撃・スキルで消費する。

アリーナはG・F・E・D・C・B・A・Sの8ランクで、勝ち進むとランクが上がる。ランクごとに敵の強さの倍率と出現するスキルのプールが変わる。ライバル4体、Sランク防衛戦、世界大会、隠しボスのオーパが用意されている。

セーブはTYPE-A/B/Cごとにスロットが分かれており、キーは `afight_save_v2_{TYPE}`。旧キーからの移行処理が入っている。

**シンクロ率**は現在値 `syncRatio` と上限 `syncMax` の2値で持つ。戦闘の補正が参照するのは現在値。上限は起動シークエンス(2-D)で初期値が決まり、育成(5-A)で引き上げる。基準値 `SYNC_BASE` は150で、現行アリーナの敵倍率はこの値(補正x1.50)を前提に調整されている。天井は `SYNC_CAP` の250(x2.10)。消耗と回復のルールはメンテナンスモード(4-B)と同時に有効化する予定で、現状は変動しない。

**新規開始はTYPE選択画面(カタログ)を経由する。** タイトルの空きスロットを押すと `handleNewGame` がカタログを開き、購入を確定すると `startNewGame` が実際にゲームを開始する。2-D 起動シークエンスと 2-E 名付けは、この2つの間に挟む想定。

詳細は `docs/` の各仕様書を参照。

## 立ち絵とバストアップ

`CHARA_ART` に登録している。同じキーの `src` と `closedSrc` は位置合わせ済みで、`naturalWidth` / `naturalHeight` を共有していること自体が「同じ枠に置ける」印になっている。切り替えても体は動かず、顔だけが変わる。

バストアップは3TYPEとも 1055x1491 の共通基準サイズで、`BUST_SIZE` 定数に出してある。目線の高さはy≒465〜505に揃っており、TYPE切り替えで顔がリサイズされて見えることはない。2-D 起動シークエンスと 4-B メンテナンスモードで共用する。

### 表情差分の作り方

生成AIに参照画像を渡す方式では位置が揃わない。参照元が同じでも毎回キャンバス全体が描き直されるため、髪や肩まで含めて絵が動く。実際に試した結果、シルエットの一致率は最良でも95%止まりだった。

確実なのは**ベースを1枚確定させ、顔だけを差し替える**方式。現在は次の手順で作っている。

1. 生成AIに、なるべく構図の近い表情差分を出させる
2. 同じく生成AIの編集機能で、顔と髪(頭部)以外を消す
3. ibisPaint で、その頭部画像を通常版の上に重ねる
4. **両眉・両目・両頬・鼻・口の5点だけを残して**、他を手作業で消す
5. 残ったレイヤーを一段上げてレイヤー統合

この方式で作ったTYPE-B / Cは、通常版とのシルエット一致率100.000%、アルファ差の最大値も4〜6に収まった。差分は目だけに限定されている。

TYPE-Aは前髪が眉の高さにあって左目が耳前の髪と重なるため、5点の切り出しが難しい。前髪と眉も含めて差し替わっており、通常版との一致率は99.918%。体は無傷なので実用上の問題はないが、目を開ける瞬間に前髪の形がわずかに変わる。フェードを挟めば見えない。

## ペーパードール (1-C / 未完了)

装備を立ち絵に重ねて表示する仕組み。データ構造は確定済みで、`index.html` の `CHARA_ANCHORS` に実測値が入っている。描画処理への接続と、型(シルエット)画像の用意が残っている。

### 設計

アンカー(接続点)は**キャラクター側**が持ち、アイテム側はアンカー名を指すだけ。逆にすると「武器N個 × TYPE M個」ぶんの定義が必要になるが、この形なら N+M で済む。

各アンカーは位置(比率)と `angle`(その部位が向いている方向)を持つ。左右の部位は角度が符号反転した鏡像の関係になる。アイテム側の `rotate` は、この向きからの差分として書く。

```
回転 = (左右反転コピーなら -item.rotate、通常なら item.rotate) + anchor.angle
```

反転させるのはアイテム自身の回転だけで、`anchor.angle` はそのまま加算する。全体を反転させると、ペア配置のときだけ正しく見えて片側だけに単体配置したときに崩れる。

### 部位 (15)

`HEAD` `HAIR` `TORSO` `WAIST` `R_BACK` `C_BACK` `L_BACK` `R_HAND` `L_HAND` `R_FOREARM` `L_FOREARM` `R_THIGH` `L_THIGH` `R_FOOT` `L_FOOT`

左右対になるのは HAND / FOREARM / THIGH / FOOT / BACK の5組。籠手やブーツのように左右で同じ形の装備は、**画像1枚を反転して2か所に置く**。1アイテムを2画像に分ける必要はない。

### 髪

髪は装備と構造が違い、体を前後から挟む2枚組になる。後ろ髪は最背面(z=2)、前髪は前面(z=34)に置き、同じ髪型として連動して切り替わる。

後ろ髪につむじから頭頂部が描き込まれているのは意図的なもので、最背面に置けばベースの頭部が覆い隠し、前髪との位置合わせがしやすくなる。

`HAIR` アンカーは `HEAD` と別に用意している。イラストの髪は頭部の輪郭より少し上に頂点が来るため、バイザー用の `HEAD`(目のあたり)とは位置が違う。

### 進捗

| | 状態 |
|---|---|
| アンカー実測 TYPE-A / B / C | 完了 |
| アンカー実測 TYPE-A髪無しベース (A0) | 完了 |
| 髪無しベース + 髪2枚 (TYPE-A) | 素材あり。ラボで確認済み |
| 髪無しベース + 髪 (TYPE-B / C) | 未着手 |
| 型(シルエット)画像 | 未着手 |
| 描画処理への接続 | 未着手 |

`DOLL_LAYERS` は形式をコメントとして記録してあるだけで、実データはまだ無い。

型画像を166点作る前に、**TYPE-Aの髪だけで描画処理を通して回転式とz順を実素材で検証しておくと安全。** 素材はラボで確認済みなので、追加の素材なしで試せる。

## tools/paperdoll_lab.html

アンカーの実測とレイヤー配置の確認を行う開発ツール。ダウンロードしてブラウザで開くだけで動く。リポジトリに置いてあるが、ゲーム本体からは参照していない。

- **アンカー定義モード** … 部位を選んでステージをタップすると、その位置にアンカーが移動する
- **レイヤー配置モード** … カテゴリー別のダミーシルエットを重ね、接続点・大きさ・回転・重なり順を調整する

調整結果は `CHARA_ANCHORS` / `DOLL_LAYERS` の形で書き出せる。ページ下部の欄に貼り戻せば復元できる。**リロードすると初期値に戻るため、中断するときは書き出した内容を控えておく。**

ラボはアンカーを実測するための開発ツールであり、ゲームに組み込む想定ではない。プレイヤーがアンカー定義をやり直すことはないため。将来プレイヤーに装備の微調整を許すなら、回転と大きさのスライダーだけを取り出した簡易版になる。

## 既知の課題

**`WEAPON_VISUALS.sword_sample` の `grip` がずれている。** `grip.y` が1205、`naturalHeight` が352で、比率にすると3.42。本来0〜1に収まるべき値が範囲外になっている。v1.31.0でソード画像を差し替えた際、`naturalHeight` は更新されたが `grip` が旧画像の座標のまま残ったもの。画像を解析した結果、柄の位置は (202, 304) 付近。ただし `rotateDeg: 200` も垂直だった旧画像用の値なので、ラボで合わせ直すのが確実。

**`R_THIGH` / `L_THIGH` の `angle` が `0` のまま。** 実測値なのか仮値なのかコードからは判別できない。脚部装甲を扱うときにラボで取り直す。

**TYPE-B / C の `HAIR` アンカーは暫定値。** 髪が描き込まれた立ち絵のため、髪無しベースができた時点で実測する。

**TYPE-Aのバストアップだけ下部に178pxの透明領域がある。** 被写体がy=1313で終わっており、TYPE-B / C はy=1490まで埋まっている。パネルを下揃えや領域いっぱいで組むとTYPE-Aだけ隙間が出る。2-D の実装時に確認する。

**`TYPE_CATALOG` の説明文は仮。** 2-C カタログに出している紹介文とキャッチコピーは世界観の裏付けがない。2-B オープニングでトーンが固まったら差し替える。
